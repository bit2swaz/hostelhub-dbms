## 1. Summary

HostelHub is a Java Swing desktop application backed by an Oracle XE database through JDBC. It replaces paper registers and spreadsheets for hostel administration. It manages blocks, rooms, student room allocations and maintenance complaints.

The Phase 1 design (ER/EER model, relational schema, normalization) is already approved. **This PRD is the source of truth for implementation, and the schema here must match the Phase 1 design exactly.** If a requirement can't be met as written, stop and flag it. Do not quietly change the design.

### Problem

Paper and spreadsheet records lead to three problems:

1. The same bed gets allocated twice.
2. Nobody can see which rooms are vacant in real time.
3. Complaints have no owner, status or deadline, so they go unresolved.

## 5. Data model

Table and column names must match the Phase 1 relational schema exactly.

- Use `GENERATED BY DEFAULT AS IDENTITY` for surrogate keys.
- All constraints are **named**, using the prefixes `pk_`, `fk_`, `uq_`, `ck_`.
- Error messages refer to constraints by these names.

### 5.1 Tables

**HOSTEL_USER**

| Column | Type | Constraints |
| --- | --- | --- |
| user_id | NUMBER | PK, identity |
| full_name | VARCHAR2(100) | NOT NULL |
| email | VARCHAR2(120) | NOT NULL, UNIQUE, CHECK basic email format |
| phone | VARCHAR2(10) | CHECK `REGEXP_LIKE(phone,'^[0-9]{10}$')` |
| password | VARCHAR2(200) | NOT NULL. Stores a PBKDF2 hash, never plain text. |
| user_role | VARCHAR2(10) | NOT NULL, CHECK IN ('STUDENT','WARDEN') |

**STUDENT** (subclass of HOSTEL_USER, mapping option 8A)

| Column | Type | Constraints |
| --- | --- | --- |
| user_id | NUMBER | PK, FK -> HOSTEL_USER ON DELETE CASCADE |
| reg_no | VARCHAR2(10) | NOT NULL, UNIQUE, CHECK `^[0-9]{2}[A-Z]{3}[0-9]{4}$` (e.g. 25BCE0231) |
| gender | CHAR(1) | NOT NULL, CHECK IN ('M','F') |
| programme | VARCHAR2(60) | NOT NULL |
| year_of_study | NUMBER(1) | NOT NULL, CHECK BETWEEN 1 AND 5 |

**BLOCK**

| Column | Type | Constraints |
| --- | --- | --- |
| block_id | NUMBER | PK, identity |
| block_name | VARCHAR2(30) | NOT NULL, UNIQUE |
| gender_type | CHAR(1) | NOT NULL, CHECK IN ('M','F') |
| num_floors | NUMBER(2) | NOT NULL, CHECK BETWEEN 1 AND 20 |

**WARDEN** (subclass of HOSTEL_USER; 1:1 MANAGES with BLOCK)

| Column | Type | Constraints |
| --- | --- | --- |
| user_id | NUMBER | PK, FK -> HOSTEL_USER ON DELETE CASCADE |
| block_id | NUMBER | NOT NULL, UNIQUE, FK -> BLOCK |
| office_no | VARCHAR2(10) | |

**ROOM** (weak entity owned by BLOCK)

| Column | Type | Constraints |
| --- | --- | --- |
| block_id | NUMBER | PK part, FK -> BLOCK |
| room_no | VARCHAR2(6) | PK part |
| floor_no | NUMBER(2) | NOT NULL, CHECK >= 0 |
| room_type | VARCHAR2(10) | NOT NULL, CHECK IN ('SINGLE','DOUBLE','TRIPLE','QUAD') |
| capacity | NUMBER(1) | NOT NULL, CHECK BETWEEN 1 AND 4 |

ROOM also has a table-level CHECK that `capacity` matches `room_type`: SINGLE=1, DOUBLE=2, TRIPLE=3, QUAD=4.

**ALLOCATION**

| Column | Type | Constraints |
| --- | --- | --- |
| alloc_id | NUMBER | PK, identity |
| student_id | NUMBER | NOT NULL, FK -> STUDENT |
| block_id, room_no | | NOT NULL, composite FK -> ROOM |
| approved_by | NUMBER | NOT NULL, FK -> WARDEN |
| start_date | DATE | NOT NULL, DEFAULT SYSDATE |
| end_date | DATE | |
| status | VARCHAR2(8) | NOT NULL, CHECK IN ('ACTIVE','VACATED') |

ALLOCATION also has these constraints:

- A table-level CHECK that `(status='ACTIVE' AND end_date IS NULL) OR (status='VACATED' AND end_date IS NOT NULL)`.
- A CHECK that `end_date >= start_date`.
- A unique function-based index `ux_alloc_one_active` on `CASE WHEN status='ACTIVE' THEN student_id END`, which enforces BR-2.

**CATEGORY**

| Column | Type | Constraints |
| --- | --- | --- |
| category_id | NUMBER | PK, identity |
| category_name | VARCHAR2(30) | NOT NULL, UNIQUE |
| sla_days | NUMBER(3) | NOT NULL, CHECK > 0 |

**STAFF**

| Column | Type | Constraints |
| --- | --- | --- |
| staff_id | NUMBER | PK, identity |
| full_name | VARCHAR2(100) | NOT NULL |
| phone | VARCHAR2(10) | CHECK 10 digits |
| category_id | NUMBER | NOT NULL, FK -> CATEGORY |

**COMPLAINT**

| Column | Type | Constraints |
| --- | --- | --- |
| complaint_id | NUMBER | PK, identity |
| student_id | NUMBER | NOT NULL, FK -> STUDENT |
| block_id, room_no | | NOT NULL, composite FK -> ROOM |
| category_id | NUMBER | NOT NULL, FK -> CATEGORY |
| staff_id | NUMBER | FK -> STAFF, nullable |
| description | VARCHAR2(500) | NOT NULL, CHECK LENGTH >= 10 |
| status | VARCHAR2(12) | NOT NULL, DEFAULT 'OPEN', CHECK IN ('OPEN','IN_PROGRESS','RESOLVED') |
| raised_on | DATE | NOT NULL, DEFAULT SYSDATE |
| resolved_on | DATE | |

COMPLAINT also has these table-level CHECKs:

- `resolved_on` is set if and only if the status is RESOLVED.
- `resolved_on >= raised_on`.
- `status = 'OPEN' OR staff_id IS NOT NULL`, meaning work can't start or finish without assigned staff.

### 5.2 Views

- **`V_ROOM_OCCUPANCY`**: block_id, block_name, room_no, floor_no, room_type, capacity, occupancy (count of ACTIVE allocations), vacancies. This is the derived `occupancy` attribute from the ER model. It is never stored.
- **`V_OVERDUE_COMPLAINTS`**: complaints that are not RESOLVED and where `SYSDATE - raised_on > sla_days`, joined with category, student, room and block names, plus `days_overdue`.

### 5.3 Triggers

Each trigger raises a named application error:

| Trigger | Timing | Rule | Error |
| --- | --- | --- | --- |
| `trg_alloc_capacity` | AFTER INSERT OR UPDATE ON ALLOCATION, **statement-level** (avoids mutating-table errors) | BR-1: no room's active count exceeds its capacity | -20001 |
| `trg_alloc_gender` | BEFORE INSERT ON ALLOCATION, row-level | BR-3: student gender = block gender_type | -20003 |
| `trg_alloc_warden_block` | BEFORE INSERT ON ALLOCATION, row-level | BR-4: approving warden manages the allocation's block | -20004 |
| `trg_complaint_staff_cat` | BEFORE INSERT OR UPDATE OF staff_id ON COMPLAINT, row-level | Staff category must match complaint category | -20005 |

### 5.4 SQL scripts (`/sql`)

Each script must run in SQL*Plus without edits:

- Use `;` for SQL statements.
- Use `/` on its own line after PL/SQL blocks.
- Include `SET DEFINE OFF` where needed.

| File | Purpose |
| --- | --- |
| `00_create_user.sql` | Run as SYSTEM. Creates the `hostelhub` user with the minimum grants (CREATE SESSION, TABLE, VIEW, TRIGGER, SEQUENCE, plus quota). |
| `01_schema.sql` | Creates all tables and constraints. |
| `02_views.sql` | Creates the views. |
| `03_triggers.sql` | Creates the triggers. |
| `04_seed.sql` | Inserts sample data (section 9). |
| `05_queries.sql` | Demo queries for SQL*Plus: joins, aggregates, views, plus deliberate constraint violations, each commented with the expected ORA error. |
| `99_drop.sql` | Drops everything in reverse dependency order. Safe to re-run. |

| ID | Requirement | Actor | Implementation notes |

## 7. Business rules: enforcement matrix

Every rule is enforced twice. The service layer gives a friendly message before the database is touched. The database is the last line of defence.

| Rule | Description | Database | Service |
| --- | --- | --- | --- |
| BR-1 | Occupancy never exceeds capacity | `trg_alloc_capacity` (-20001) | Locks the room row, counts, rejects if full |
| BR-2 | At most one ACTIVE allocation per student | `ux_alloc_one_active` (ORA-00001) | Checks before insert |
| BR-3 | Student gender matches block gender_type | `trg_alloc_gender` (-20003) | Filters the student/room pickers and validates |
| BR-4 | Warden manages exactly one block and acts only on it | `uq_warden_block` + `trg_alloc_warden_block` (-20004) | Every warden query and action is scoped to their block_id |
| BR-5 | Status in {OPEN, IN_PROGRESS, RESOLVED}; resolved_on >= raised_on | CHECK constraints | Forward-only state machine |
| BR-6 | Overdue once open longer than the category's sla_days | `V_OVERDUE_COMPLAINTS` | Overdue flag in tables and reports |

## 8. Architecture

Three tiers, matching slide 7 of the deck:

```
Swing UI  ->  Service layer (rules, transactions)  ->  DAO (JDBC PreparedStatement)  ->  ojdbc11  ->  Oracle XE
```

```
hostelhub/
├── pom.xml
├── README.md
├── PRD.md
├── sql/                       # SQL*Plus scripts (section 5.4)
├── docs/
│   ├── TEST_CASES.md          # Phase 3 test-case table
│   └── screenshots/           # every screen, for the report
├── .github/workflows/ci.yml
└── src/
    ├── main/java/com/hostelhub/
    │   ├── App.java
    │   ├── config/DbConfig.java          # db.properties + env overrides
    │   ├── db/ConnectionFactory.java
    │   ├── db/SqlScriptRunner.java       # handles ; and / terminators
    │   ├── model/                        # records: Student, Room, Allocation, Complaint ...
    │   ├── dao/                          # one DAO per table; SQL only here
    │   ├── service/                      # Auth, Student, Room, Allocation, Complaint, Report
    │   ├── service/ServiceException.java
    │   ├── ui/                           # LoginFrame, StudentDashboard, WardenDashboard, panels, dialogs
    │   └── util/                         # PasswordHasher, OracleErrorMapper, Session
    ├── main/resources/db.properties
    └── test/java/com/hostelhub/
        ├── support/OracleTestBase.java   # one shared Testcontainers instance, runs sql/01-04
        ├── db/                           # constraint + trigger tests
        ├── service/                      # service + DAO tests
        └── ui/                           # AssertJ Swing tests
```

### Rules for the code

- **SQL only in DAOs**, always through `PreparedStatement`. String-concatenated SQL is never allowed.
- **Services own transactions.** They call `setAutoCommit(false)`, then commit or roll back, and always close resources (try-with-resources).
- **UI never touches JDBC.** Long operations use `SwingWorker` so the window doesn't freeze.
- **Config** comes from `db.properties` (default `jdbc:oracle:thin:@localhost:1521/XEPDB1`, user `hostelhub`). The env vars `HOSTELHUB_DB_URL`, `HOSTELHUB_DB_USER` and `HOSTELHUB_DB_PASSWORD` override it.
- **Passwords** use `PBKDF2WithHmacSHA256` from the JDK, stored as `pbkdf2$<iterations>$<saltB64>$<hashB64>`.
- **Errors:** `OracleErrorMapper` turns ORA-00001, ORA-02290, ORA-02291, ORA-02292 and ORA-20001 to -20005 into plain-English messages that name the rule (e.g. "Room A-101 is full (BR-1)."). Stack traces are never shown to the user.
- **Session:** a simple in-memory `Session` holds the logged-in user, role and (for wardens) block_id.

- Wardens: `warden.a@hostelhub.test`, `warden.b@hostelhub.test`, `warden.c@hostelhub.test`

## 11. Testing and verification

All tests run with `mvn verify` against a **real Oracle database** started by Testcontainers. The suite must pass with no manual steps beyond having Docker running.

### 11.1 Database tests (`db/`)

- One test per CHECK, UNIQUE, FK and trigger, asserting the exact ORA code. These are the Phase 3 constraint-violation cases.
- View tests: occupancy equals the count of ACTIVE allocations, and the seeded overdue complaints appear in V_OVERDUE_COMPLAINTS.

### 11.2 Service and DAO tests (`service/`)

- **Happy path** for every FR.
- **Every BR rejected at the service layer**, with the expected message.
- **Transactions:** a failed transfer leaves the original allocation ACTIVE (rollback works).
- **Concurrency:** two threads allocate the last bed of a room at the same time, and exactly one succeeds.

### 11.3 GUI tests (`ui/`, AssertJ Swing)

- Run headless on Linux via `xvfb-run`.
- Tagged `@Tag("gui")` so they can be skipped with `-DexcludedGroups=gui`.

Flows to cover:

- Bad login shows an error.
- Student logs in and raises a complaint, which then appears in the table.
- Warden allocates a student to a room.
- Allocating to a full room shows the BR-1 message.
- Warden assigns staff and resolves a complaint.
- Warden deletes a room that has history, which is blocked with a message.

Each flow saves a screenshot to `target/screenshots/`.

### 11.4 Visual check

1. Launch the real app under Xvfb against the seeded database.
2. Capture every screen in section 10.
3. Inspect the images for clipped text, broken layouts and empty tables.
4. Copy the final set to `docs/screenshots/`.

### 11.5 Test-case document (`docs/TEST_CASES.md`)

- At least 30 cases.
- Columns: ID · Type (functional / constraint / error handling / UI) · FR/BR covered · Steps · Expected · Actual · Result.
- Each row links to its automated test where one exists.
- Every FR and BR is covered at least once.

### 11.6 CI

`.github/workflows/ci.yml` runs `mvn -B verify` on `ubuntu-latest` (Docker is available there), with the GUI tests under `xvfb-run`. It uploads the JaCoCo report and screenshots as artifacts.

## 14. Assumptions and open questions

- **FR-02:** blocks are created in setup SQL, not the UI, because every block needs a warden (MANAGES is total on both sides). Wardens can edit their own block and fully manage its rooms.
- **Transfers:** only within the warden's own block, following BR-4.
- **Allocation status values:** ACTIVE and VACATED. These were not stated in the Phase 1 deck; this PRD fixes them.
- **Deleting records:** students and rooms with any history can't be deleted. Records are kept for audit, with no soft delete.
